# Crucible — hackathon submission

## One sentence

Crucible is a developer CLI that connects an npm audit warning to a replayable security experiment, compares repairs, and notices when saved evidence goes stale.

## Problem and approach

A dependency alert does not explain whether the application exposes the vulnerable behavior. Engineers still have to investigate it, try repairs, check that legitimate features survive, and explain their decision to another person.

Crucible brings those steps into a local workflow. Its distinctive demonstration is a patch that blocks the trigger but breaks currency rendering: a scanner result alone would not show that tradeoff. The tool preserves both observations so a developer can choose the better repair.

## Three-minute walkthrough

Run from the repository root after `npm ci && npm run build`. Use Node 24. The replay needs the existing prepared Dockside installation; rehearse once before recording. Live preparation is visible and may take more than a minute for all three environments. If using recorded output, identify it as recorded.

1. **The warning.**

   ```sh
   node dist/cli.js scan capsules/invoice/replay --audit examples/invoice-audit.json
   node dist/cli.js explain GHSA-r5fr-rjxr-66jc
   ```

   “We keep every finding, including unsupported ones. For this advisory we can point to candidate template calls and explain the triggering condition. That is investigation guidance, not proof that the code is exploitable.”

2. **The experiment.**

   ```sh
   node dist/cli.js demo
   ```

   “The same external checks run against three disposable applications. The original executes our harmless marker. Removing the feature stops it but breaks euro invoices. The reviewed guard blocks the trigger and preserves all four declared checks.”

   “This runs our curated example. It does not automatically clone or test the repository supplied to `scan`. The repairs are authored fixture patches, not generated by an AI agent.”

3. **Evidence that stays reviewable.**

   Prepare a single repaired run before the presentation; choose a new filename if it exists:

   ```sh
   node dist/cli.js replay invoice --revision fixed --out evidence/replays/presentation-fixed.json
   node dist/cli.js verify evidence/replays/presentation-fixed.json
   node dist/cli.js report evidence/replays/presentation-fixed.json
   ```

   Add a comment to `capsules/invoice/replay/patches/fixed.ts`, then repeat `verify`. It must say `EVIDENCE_STALE`. Undo the comment afterward.

   “An input changed. We ask for revalidation instead of silently carrying the old conclusion forward. This first version tracks files conservatively; it does not understand every semantic change.”

## What to submit

- The repository, including source, fixtures, the sample audit report, and setup documentation.
- A recording of the actual commands and outcomes.
- A saved JSON replay and its Markdown report.
- The measured test/run results from `VERIFICATION.md`.

Do not include `.crucible/`: it contains local Dockside sessions and management configuration. It is ignored by Git. No remote repository or submission has been created automatically.

## Scope and next work

The current product is a one-advisory CLI prototype. The broader product would maintain a reviewed capsule library, adapt tests to a customer's actual application, support more frameworks, and connect replay to CI and PRs. Before making those promises, test independent repositories, clean-machine installation, additional vulnerability classes, and whether developers find the evidence useful enough to keep running.

The key open question is whether reusable experiments save more investigation work than they cost to author and maintain. This demonstration establishes the workflow, not the commercial answer.
